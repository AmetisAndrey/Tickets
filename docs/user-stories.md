# Пользовательские истории и критерии приёмки

Критерии проверяются через REST API и автоматизированные тесты.

## US-01. Регистрация заявки
**Как** сотрудник, принимающий обращение, **я хочу** создать заявку с заголовком, описанием, категорией, приоритетом и сроком, **чтобы** зарегистрировать обращение в единой системе.

Критерии:
1. Корректный `POST /api/tickets` возвращает HTTP 201 и `Location` созданной заявки.
2. Новая заявка имеет статус NEW, `createdAt` устанавливается сервером.
3. В истории создаётся запись `fromStatus=null`, `toStatus=NEW`.
4. Пустой title или отсутствующее обязательное поле дают HTTP 400.
5. Несуществующая категория даёт HTTP 404.

## US-02. Просмотр заявки
**Как** специалист, **я хочу** получить заявку по ID, **чтобы** увидеть её параметры и состояние.

Критерии: существующий ID — HTTP 200 с полями заявки; неизвестный ID — HTTP 404; ответ содержит категорию, приоритет, статус, даты создания, срока и закрытия.

## US-03. Редактирование открытой заявки
**Как** специалист, **я хочу** менять описание, приоритет и срок, **чтобы** поддерживать данные актуальными.

Критерии: `PATCH /api/tickets/{id}` изменяет только переданные ненулевые поля; остальные остаются прежними; для RESOLVED/CANCELLED возвращается HTTP 409; неизвестный ID даёт 404. Заголовок и категория текущим DTO не редактируются.

## US-04. Начало обработки
**Как** специалист, **я хочу** перевести NEW в IN_PROGRESS, **чтобы** зафиксировать начало работы.

Критерии: переход NEW → IN_PROGRESS даёт 200 и запись истории; запрещённый переход даёт 409; при отказе статус и история не меняются.

## US-05. Завершение или отмена
**Как** специалист, **я хочу** завершить или отменить заявку, **чтобы** зафиксировать результат.

Критерии:
1. Разрешены IN_PROGRESS → RESOLVED, NEW → CANCELLED и IN_PROGRESS → CANCELLED.
2. NEW → RESOLVED запрещён (409).
3. При RESOLVED/CANCELLED устанавливается `closedAt`.
4. Закрытую/отменённую заявку нельзя редактировать или повторно открыть.
5. Статус и история изменяются атомарно.

## US-06. Просмотр истории
**Как** специалист или руководитель, **я хочу** просматривать историю статусов, **чтобы** восстановить ход обработки.

Критерии: `GET /api/tickets/{id}/history` возвращает 200 и записи по `changedAt` по возрастанию; есть начальная запись null → NEW; неизвестный ID даёт 404.

## US-07. Поиск заявок
**Как** специалист, **я хочу** фильтровать заявки, **чтобы** быстро находить нужные.

Критерии: `GET /api/tickets` поддерживает `status`, `priority`, `categoryId`, `overdue`, `page`, `size`; фильтры статус/приоритет/категория комбинируются; `overdue=true` выбирает только просроченные NEW/IN_PROGRESS; по умолчанию page=0, size=20, сортировка createdAt DESC. Для `overdue=false` в текущем коде отдельная фильтрация отсутствует (D-03).

## US-08. Справочник категорий
**Как** сотрудник, **я хочу** получить категории, **чтобы** выбрать категорию при создании.

Критерии: `GET /api/categories` возвращает 200 и массив `id`, `name`; миграция добавляет Hardware, Software, Network, Access.

## US-09. Сводный отчёт
**Как** руководитель, **я хочу** получить статистику за период, **чтобы** оценить нагрузку и результаты.

Критерии: `GET /api/reports/summary` принимает ISO-8601 `from`, `to`; выборка по полуоткрытому интервалу `[from,to)`; ответ содержит `totalCreated`, `byStatus`, `byPriority`, `openOverdue`, `avgResolutionMinutes`; среднее рассчитывается только для RESOLVED с `closedAt`; если таких нет — null; `from >= to` даёт HTTP 400.

## Связь историй с требованиями

| История | Требования | Основные проверки |
|---|---|---|
| US-01 | FR-01, FR-02, FR-07 | Создание, валидация, начальная история |
| US-02 | FR-03 | GET, неизвестный ID |
| US-03 | FR-04, FR-05 | Обновление и запрет редактирования |
| US-04 | FR-06, FR-07 | Разрешённый переход и история |
| US-05 | FR-06, FR-07 | Матрица переходов, closedAt, атомарность |
| US-06 | FR-08 | История и 404 |
| US-07 | FR-09–FR-11 | Фильтры, просрочка, пагинация |
| US-08 | FR-12 | Справочник категорий |
| US-09 | FR-13 | Границы периода и агрегаты |
